# Профилирование и оптимизация начала попытки

## Сценарий и решение

Измеряется `AttemptManager.start(student, test)`, когда активной попытки нет:
проверка доступности, получение корректного банка с вариантами, транзакция,
создание Attempt и полного набора снимков, назначение первого вопроса и commit.
Возврат существующей попытки не является измеряемым быстрым путём.

Baseline — services.py из commit `b45d5c667cbaf7d1d2d89f6ecfebd3ca4b617dde`,
загружаемый через `git show` в отдельный Python-модуль с прежними моделями.
Исходная реализация не ухудшалась: в ней был один `objects.create` на снимок.
Финальная — services.py рабочего дерева с SHA-256 в benchmark-final.json и
source-manifest.json. Исправление D2 входит в итоговую версию; на успешном
измеряемом пути его обработчик не выполняется.

`cProfile` baseline на 2000 вопросах показал 2001 вызов QuerySet.create и
существенные затраты на save/SQL compiler. Отдельный счётчик SQL подтвердил
2000 INSERT снимков и 2008 операций всего. Это основание выбрать пакетную запись,
а не менять алгоритм ближайшего уровня или случайный выбор.

Внесено одно изменение пути сохранения: список AttemptQuestion передаётся
`bulk_create` в прежнем `transaction.atomic`. Порядок исходного банка и снимков,
состав полей, фильтрация корректности и вызов `_choose` сохранены. Django сам
разбивает вставку согласно ограничению числа SQL-параметров SQLite: это не один
неограниченно большой INSERT для всех размеров.

## Воспроизводимость и методика

Команды (запускать последовательно, без параллельных тестов/benchmark):

```powershell
.\.venv\Scripts\python -X utf8 tools/practice2_benchmark.py --variant baseline
.\.venv\Scripts\python -X utf8 tools/practice2_benchmark.py --variant final
.\.venv\Scripts\python -X utf8 tools/practice2_artifacts.py
```

* Размеры банков: **50** (обычный учебный объём), **500**, **2000** (масштабирование).
  Каждый вопрос имеет четыре варианта, один правильный, сложность циклически 1–5.
  length=10, initial=3; случайность QuestionSelector — Random(42).
* Каждый процесс создаёт собственный SQLite-файл во временном каталоге, применяет
  миграции, создаёт пользователя без пароля и синтетический банк. Пользовательская
  база не читается и не используется. Подготовка Question/Option/M2M не измеряется.
* Перед каждым измерением активных попыток нет. После вызова вне измеряемого
  участка удаляется Attempt с каскадными снимками/ответами. Банк остаётся одинаковым.
  Каждый следующий размер добавляет новую тему и банк одинаково в обеих версиях.
* **1 прогрев**, затем **7** вызовов с `time.perf_counter`; показана медиана.
  Все индивидуальные значения сохранены в JSON. Профилирование и tracemalloc
  не включены в тайминг этих семи повторов.
* Память: отдельный прогон `tracemalloc.start()` → start → get_traced_memory peak.
  Это пик Python-аллокаций измеряемого участка, **не RSS** процесса и не память
  нативного движка SQLite. GC остаётся в обычном режиме в обоих вариантах.
* SQL: отдельный прогон с `connection.execute_wrapper`; считаются обращения
  execute (включая BEGIN), INSERT и INSERT таблицы снимков. Подготовка/очистка
  не считаются. COMMIT через DB-API может не проходить execute-wrapper, поэтому
  показатель назван числом перехваченных SQL-операций, а не сетевых round trips.
* Операции Python: total_calls из отдельного cProfile-прогона; отдельно показано
  неизменное число созданных снимков. Это не аппаратные инструкции процессора.
* Файлы `profile-{baseline,final}-{50,500,2000}.txt` содержат фактические top-35
  cumulative statistics. Время под профилировщиком не подменяет чистый benchmark.
* Последовательные итоговые прогоны сохранены в benchmark-*-run.txt с exit=0;
  настройки и инструменты одной машины одинаковы. Нет замеров на сервере или
  статистического доверительного интервала; разброс виден в семи исходных значениях.

## Результаты

Точная итоговая таблица с миллисекундами, памятью, SQL, INSERT и вызовами:
`results/benchmark-comparison.csv`. Первичные значения:
`results/benchmark-baseline.json`, `results/benchmark-final.json`.

| Вопросов | До, мс (медиана) | После, мс (медиана) | Улучшение времени | SQL до → после | Пик Python до → после, байт |
|---:|---:|---:|---:|---|---|
| 50 | 26,010 | 29,495 | **−13,40%** | 58 → 9 | 334614 → 369526 |
| 500 | 164,863 | 85,043 | **48,42%** | 508 → 14 | 3162676 → 3209352 |
| 2000 | 648,239 | 343,193 | **47,06%** | 2008 → 31 | 13724790 → 13770756 |

Число профилируемых Python-вызовов: 50267 → 40142, 441540 → 338165,
1745610 → 1331455 соответственно. Число снимков остаётся 50/500/2000.
INSERT снимков: 50 → 1, 500 → 6, 2000 → 23.

Процент вычисляется как `(median_before − median_after) / median_before × 100`.
На банках 500 и 2000 измеренное ускорение превышает требование 10–15%.
На 50 вопросах последний сохранённый прогон не подтвердил ускорение: медиана
финальной версии оказалась выше baseline. Этот отрицательный результат сохранён,
повторный прогон ради получения положительного процента не выполнялся.
На небольшом банке стоимость запуска/фиксации и внешняя вариативность машины
существенны относительно самой вставки; причинность замедления этими факторами
отдельно не доказана. Решение оправдано масштабированием и сокращением SQL,
а гарантия ускорения любого малого банка не заявляется.
Память немного увеличилась из-за списка объектов для пакетной вставки;
уменьшение памяти **не заявляется**. Остаётся O(n) полный банк снимков,
что требуется для неизменности попытки.

## Эквивалентность и ORM

Для каждого размера после отдельного profile-прогона сохранена SHA-256 сигнатура
всех полей снимков (source_id, текст, сложность, массив вариантов, правильный индекс,
пояснение) и траектории десяти правильных ответов (source_id, факт/цель, reason).
До/после сигнатуры совпали. Недетерминированные timestamp и PK самих попыток не
включаются. Десять source_id уникальны, состояние COMPLETED.
Генератор итоговых артефактов автоматически проверяет совпадение сигнатур.

| Риск | Подтверждение |
|---|---|
| Ближайший уровень и меньший при равенстве | Старые AlgorithmTests; новый driver и перестановка входного банка |
| Seed и отсутствие повторений | Старый test_seed_reproducible_and_no_repeats; сигнатуры benchmark |
| Неизменность снимков | Старый test_snapshot_entire_bank редактирует исходники; новый test_snapshot_source_contract |
| Корректное завершение | Полные service/HTTP-сценарии, length=1 и 3, benchmark length=10 |
| Rollback создания/ответа | Ошибка после создания снимков; реальная UNIQUE-ошибка; ошибки answer в пяти точках |
| Валидация | valid_bank оставлен; и create/save, и bulk_create сами не вызывают full_clean. Формы и SQL constraints сохранены |
| Ограничения БД | Реальное нарушение snapshot_source даёт IntegrityError; после отката нет частичных строк |
| Сигналы и save override | test_snapshot_orm_contract подтверждает отсутствие override и pre_save/post_save listeners для AttemptQuestion |
| Получение PK | SQLite возвращает PK bulk_create; `_choose` всё равно читает сохранённые строки из БД; current_id заполнен |
| Конкурентность | Прежний двухпоточный тест ответа прошёл; обработка гонки start дополнительно проверена stub, не нагрузочным тестом |

Если в будущем появятся save override, сигналы или другая СУБД, предпосылки
пакетной записи нужно пересмотреть. Это ограничение применимости текущего решения,
а не обнаруженная регрессия.
